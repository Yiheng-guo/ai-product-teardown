# 产品决策模式

用于回答：谁会在什么场景使用它、AI 带来什么增量、体验哪里影响结果、下一步值得验证什么。无需先生成 Agent 契约或技术架构。

## 先确定决策问题

从现有材料提取目标用户、具体任务、当前替代方案、成功标准、使用频率和约束。缺失字段标为未知；只询问会改变分析方向的信息。不要把自己假想的用户画像当成访谈结果。

证据不足时仍可完成有限的桌面研究，但将“官方宣称”“实际观察”“用户反馈”分开。只有落地页时不评判真实生成质量、完成率、留存或付费意愿。没有实验授权时，用已提供的操作记录分析，不启动生成来补齐表格。

## 沿一个核心任务分析价值

1. 起点：什么事件触发任务，用户带着什么输入与限制进入？
2. 首次价值：什么具体、可检查的结果算获得价值？注册完成、生成开始和 Agent 回复“完成”通常不够。
3. 完成过程：输入准备 → 首次结果 → 检查 → 修改 → 可用交付。对每步标注用户操作、产品反馈、结果、返工和证据 ID。
4. 再次使用：历史内容、项目上下文、模板或协作是否减少下次成本？UI 中存在历史入口不能证明实际留存。
5. 退出与替代：用户何时可能转回人工、通用模型或旧流程？把原因写成待验证假设，除非有直接反馈。

评价 AI 增量时比较同一任务的非 AI 基线：输入准备、等待、结果检查、返工、交接成本是否减少，结果是否达到相同验收标准。没有基线数据就列需要测量的差值，不编造“效率提升 X%”。

## 识别 AI 特有的问题

按观察相关性选择，不强制凑齐：输入缺失时是否澄清；生成结果是否可核验；错误是否可恢复；修改范围是否可控；上下文能否复用；结果能否编辑和交付；耗时、额度和失败扣费是否可理解。将模型质量问题与流程、状态、界面问题区分开，根因不可见时保留多个解释。

## 商业判断的证据边界

定价记录需注明查询日期、地区、币种、套餐、月付/年付、税费口径与额度单位；不可访问时写未知。标价、实际扣款、业务 API 配额和底层模型成本分别记录。

不要从积分消耗推断供应商成本、毛利、付费转化或营收。只有用户请求成本测算且输入可得时才给区间估算，列出单次调用成本、失败重试次数、成功率和敏感性假设。成本估算仍归为推断。

## 从发现到改进

用链条组织每项建议：**观察 E-ID → 受影响任务 → 影响机制 → 建议 → 验证方法**。建议本身标为【建议设计】，不要因为起点有证据就变成事实。

优先级使用有解释的类别：

- P0：已观察到核心交付无法完成、错误完成状态或重要结果丢失；注明发生条件与样本范围。
- P1：任务可完成，但观察到明显返工、理解或控制成本。
- P2：次要优化或证据薄弱的机会，先做低成本验证。

同时列证据强度、影响范围是否已知、实施依赖及工作量是否仅为估计。严重问题与低置信度可以并存；不要用伪精确总分掩盖它。样本不足时先安排验证，不把一次失败写成普遍故障。

每个优先验证的机会写一张实验卡：

| 字段 | 内容 |
|---|---|
| 假设 | 对哪类用户、哪项任务、什么改变可能带来什么结果 |
| 对照与条件 | 现状/方案，固定输入、版本、套餐与任务难度 |
| 主指标 | 明确分子分母或计时起止点，例如首次可用结果时间 |
| 护栏 | 结果质量、误操作、费用或返工不可恶化的条件 |
| 判定标准 | 有来源的阈值，或明确标为待校准的建议阈值 |
| 样本与周期 | 实际样本和局限；计划数量不写成已执行数量 |
| 结果与行动 | 未执行写未执行；区分继续、修改、停止的条件 |

## 交付与核验

使用 [产品决策模板](../assets/product-decision-template.md)，按需要删减。结论先行，保留来源索引；无需为了填模板制造内容。参考 [虚构示例](../examples/product-decision-demo.md) 理解证据边界，该示例不是现实产品数据。

交付前检查：核心结论可回到证据；商业数字有来源或明确假设；建议有验证办法；不足的样本没有被外推；未执行的实验没有结果；无 Agent 的产品没有被硬塞 Agent 架构。
